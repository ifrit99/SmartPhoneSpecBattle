# RFC: キャラクターアート刷新（成人女性擬人化）

- ステータス: **DRAFT（提案・未承認）**
- 作成日: 2026-09-03
- 種別: 設計提案（ドキュメントのみ / プロダクトコード変更なし）
- 対象領域: `lib/presentation/widgets/pixel_character.dart` および同ウィジェットを参照する全画面
- 非対象: ドメイン層（`Character` / `CharacterCodec` / `CharacterGenerator`）、バトルロジック、バランス調整

---

## 1. このRFCの目的

現行のキャラクター表現である 12×12 マス相当の `CustomPaint` ドット絵を、
**成人女性として読める擬人化キャラクターアート**へ置き換えるための、
スタイル方針・アセットパイプライン・データマッピング・移行計画を定義する。

このRFCは合意形成のための文書であり、以下は**含まない**:

- Dart / Flutter のプロダクトコード変更
- 最終的なキャラクターPNG／画像アセットの生成
- マージ（本RFCはドキュメント専用PRとして提出し、レビュー後に判断する）

---

## 2. 背景と現状

### 2-1. 現行のアート実装

`PixelCharacter`（`lib/presentation/widgets/pixel_character.dart`）は、
`Character` の 7 個の整数フィールドから 12×12 グリッド上に矩形を描き分ける
手続き的レンダラである。

| フィールド | 現行の意味 | 現行バリエーション数 |
|---|---|---|
| `headIndex` | 頭部形状（丸／角／とがり／ヘルメット等） | 8 |
| `bodyIndex` | 胴体形状（幅・逆三角・丸型等） | 6 |
| `armIndex` | 腕の長さ・太さ・向き | 5 |
| `legIndex` | 脚の幅・長さ・スタンス | 5 |
| `colorPaletteIndex` | 3色パレット | 12 |
| `accessoryIndex` | 装飾（0 = なし） | 8 |
| `auraIndex` | 背面エフェクト（0 = なし） | 6 |

理論上の組み合わせは **691,200 通り**。
ただし `CharacterGenerator.generate` は `colorPaletteIndex` に `random.nextInt(6)`
しか渡しておらず、実際にシードから生成されるパレットは 0–5 の 6 種に留まっている
（`AvatarCustomization.paletteVariations = 12` とは不一致。既存の齟齬であり本RFCでは修正対象としない）。

### 2-2. 現行の表示コンテキスト

| 画面 | 表示サイズ | 備考 |
|---|---|---|
| バトル画面 | `width * 0.18` を 50–100px にクランプ | 静かな夜景背景の上に自機・敵機を配置 |
| キャラクター詳細 | 可変（大きめ） | 主役表示 |
| ガチャ演出 / 結果 | 80px | 排出時の見せ場 |
| インベントリ / 編成 | 100px / 52px | 一覧とカード |
| 図鑑・Powerカード | 24px / 28px | 極小スロット |
| URL共有・ゲストプレビュー | 70px 前後 | 対戦前の確認 |

**重要な制約**: バトル画面の最大 100px は、描き込みのある成人女性の全身立ち絵にとって
明確に不足する。24–28px の一覧スロットに至っては、立ち絵は原理的に判別不能である。
この点は §7（12×12の扱い）と §11（未決事項）で扱う。

### 2-3. 維持しなければならない既存の仕組み

| 仕組み | 内容 | 本RFCでの扱い |
|---|---|---|
| シード生成 | `CharacterGenerator.generateSeed` が端末スペックから決定論的にシードを作る | **維持**（変更なし） |
| 6属性 | `ElementType` = fire / water / earth / wind / light / dark、相性倍率あり | **維持**（変更なし） |
| ガチャレアリティ | `Rarity` = N / R / SR / SSR、`statMultiplier` あり | **維持**（変更なし） |
| URL対戦 | `CharacterCodec` v3。ビジュアル7バイトを含む Base64url + HMAC 4バイト | **維持**（バイト列を1バイトも変更しない） |
| 静かなバトル背景 | `assets/images/battle_bg.png`（暗い夜景、低彩度） | **維持**（差し替えない） |

## 3. ゴールと非ゴール

### ゴール

1. キャラクターが**成人女性として明確に読める**こと。年齢的に曖昧・幼く見える表現を構造的に排除する。
2. 「端末スペック＝キャラクター」というコンセプトを損なわず、擬人化として自然に接続すること。
3. 静かな夜景バトル背景の上で、背景を壊さずにキャラクターが視認できること。
4. シード・6属性・ガチャレアリティ・URL対戦を**一切変更せずに**アートだけを差し替えられること。
5. アセット0枚の状態でもアプリが完全に動作すること（段階導入可能であること）。

### 非ゴール

- 現行の 691,200 通りの見た目バリエーションを維持すること（§6-4 参照。**明示的に諦める**）
- バトルロジック・ステータス計算・バランスへの影響
- アニメーション（待機・攻撃モーション）の導入。第1弾では静止画のみとする
- 3Dモデル・Live2D 等のランタイム導入

## 4. アートディレクション（スタイル提案）

### 4-1. 世界観の軸

本アプリのキャラクターは「端末スペックから生成される存在」である。
したがって擬人化の主語は **属性ではなく端末** とする。

> プレイヤーのキャラクターは、**そのプレイヤーの端末が人の姿をとったもの**。
> ガチャキャラクターは、架空17機種それぞれが人の姿をとったもの。
> 属性（OSバージョン由来）は、その人物に宿る「系統色」として表現される。

この軸により、CPU コア数＝出力、RAM＝耐久、ストレージ＝装甲、バッテリー＝機動、
という既存のステータス写像が、そのまま人物の職能・装備のデザイン言語になる。

### 4-2. ビジュアルスタイル

| 項目 | 方針 |
|---|---|
| 画風 | セミフラットのアニメ塗り。線は細めの単色線画、影は 2 段（本影＋落ち影）まで |
| 頭身 | **7〜7.5頭身**。デフォルメ・ちび頭身は採用しない |
| 主題 | 「機材を扱う専門職の成人女性」。オペレーター／整備士／通信技師／観測員 等 |
| 情報量 | シルエット優先。ディテールは腰から上に集中させ、脚部は面で処理する |
| 彩度 | 中〜低彩度を基調。彩度の高い色は属性色のアクセント面（全体の 10% 以下）に限定 |
| 輪郭 | 背景から浮かせるため、**属性色のリムライトを片側 1 本**入れる（不透明度 50–70%） |
| 発光 | 白フチ・全体グロー・強いブルームは使わない（静かな背景と衝突するため） |
| 接地 | 足元に低不透明度の楕円コンタクトシャドウを必ず置き、浮きを防ぐ |
| 構図 | 全身立ち、正面〜3/4。カメラは水平（あおり・俯瞰を使わない） |

### 4-3. 「成人として読める」ための必須基準

以下は**任意の指針ではなく、納品受け入れの合否基準**とする。
1項目でも満たさないアセットは受け入れない。

**必須（すべて満たすこと）**

- [ ] 7〜7.5頭身。頭部が身長の 1/7 より大きくないこと
- [ ] 目の縦横比が 1:1 未満（縦に大きい丸目にしない）。目の上下位置が頭部の縦中央またはそれ以下
- [ ] 鼻梁と顎のラインが線または影で明示されていること
- [ ] 首の長さ・肩幅・鎖骨が成人の骨格として描かれていること
- [ ] 手が顔の大きさに対して小さすぎないこと（成人比率）
- [ ] 表情の基調が「職務中の落ち着き」。上目遣い・涙目・頬の赤みを基調にしない
- [ ] 服装は職能を示す機能的デザイン（作業着・制服・防護装備）であること

**禁止（1つでも該当したら差し戻し）**

- [ ] 学齢を連想させるモチーフ（学生服、ランドセル、通学鞄、教室小物など）
- [ ] 幼児体型・幼児比率の示唆
- [ ] 性的に強調された構図・ポーズ・カメラアングル
- [ ] キャラクターの設定年齢が未記載、または 20 歳未満

**運用**

- 各キャラクターは**キャラクターシート**（正面全身・表情差分・設定年齢・職能・属性）を先に起こし、
  シート段階でこのチェックリストを通過させてから本制作に入る。
- 設定年齢は **26〜38歳** のレンジで各キャラに明記し、後述の `manifest.json` にメタデータとして保持する。
- 納品時に同じチェックリストで再確認し、結果を `docs/plans/` の該当計画ファイルに記録する。

### 4-4. 背景（静かな夜景）との両立

背景は差し替えず、**キャラクター側を背景に合わせる**。

- 背景の平均輝度は低く彩度も低い。キャラクターの中間調を背景より 1.5〜2 段明るく置くことで、
  彩度を上げずに分離する。
- 分離の主役は**リムライト**。属性色（`elementColor`）と同系の色を片側に入れる。
  これによりバトル画面で属性が一目で分かり、既存の属性色UIとも整合する。
- キャラクターの背後に半径の大きい極低不透明度（8–12%）の暗い楕円を敷き、
  背景のビル群のディテールがシルエットに食い込むのを防ぐ。
- 既存の `_drawAura` 相当のエフェクトは**アセットではなく手続き描画のまま**残し、
  属性色で描く（§6-3）。アセット化するとファイル数が 6 倍になり、静かさも壊れるため。

## 5. ロスター設計

### 5-1. 2つの案

| | 案A: 属性ベース + 衣装ティア | 案B: ガチャ端末ごとの固有キャラ |
|---|---|---|
| 構成 | 6属性 × 衣装ティア3段 = 18立ち絵 | 架空端末カタログ17機種 = 17人（+ シード生成用の汎用6人） |
| 納得感 | 中（属性が人物の系統） | 高（「この端末の子」が成立する） |
| 制作コスト | 低〜中 | 高 |
| シード生成キャラへの適用 | そのまま適用可 | 別途汎用ベースが必要 |
| 拡張 | 端末固有キャラを後から差し込める | 端末追加のたびに1体必要 |

### 5-2. 推奨

**v1 は案A、将来的に案B を上乗せする。**

- v1: 属性6 × 衣装ティア3（N/R = 標準、SR = 強化、SSR = 特装）= **18立ち絵**
- v2 以降: SSR 3機種など「見せ場のある端末」にのみ固有立ち絵を追加し、
  resolver の解決順で属性ベースより優先させる（§6-2 の解決順に組み込み済み）

衣装ティアはレアリティに紐づくが、**シード生成キャラ（＝プレイヤー自身の端末）にはレアリティが無い**。
この場合は標準ティアを使う。これは既存の `CharacterCodec` の flags における
`isGacha` ビットの有無とそのまま対応する。

## 6. seed → アートのマッピング

### 6-1. 大原則

**マッピングは presentation 層に閉じた純粋関数とする。**

```
resolveArt(Character, {Rarity?}) -> ArtKey?
```

- ドメイン層（`Character` / `CharacterCodec` / `CharacterGenerator`）は 1 行も変更しない
- 新しいバイト（例: `artId`）を codec に追加**しない**。既存の7バイトから導出する
- 解決不能なら `null` を返し、呼び出し側は `PixelCharacter` にフォールバックする

### 6-2. マッピング表（v1）

| 入力 | 出力 | v1での扱い |
|---|---|---|
| `element`（6） | ベース人物の系統 | **採用**（6ベース） |
| `rarity`（4、ガチャのみ） | 衣装ティア（N/R→標準、SR→強化、SSR→特装） | **採用**（3ティア） |
| `colorPaletteIndex`（12） | アクセントマスクへのティント色 | **採用**（アセット追加なし、§6-3） |
| `accessoryIndex`（1–7） | 頭部アンカー基準のオーバーレイ画像 | **採用**（7枚、ベース非依存） |
| `auraIndex`（1–5） | 手続き描画エフェクト（属性色） | **採用**（現行 `_drawAura` 相当を流用） |
| `headIndex`（8） | 表情差分ID | **v1では未使用**（resolver は受け取るが解決に使わない。v2 で per-base 表情差分をアセット化） |
| `bodyIndex`（6） | 装備シルエット差分 | **v1では未使用**（将来のレイヤー拡張点として manifest に予約） |
| `armIndex`（5） | 携行機材差分 | **v1では未使用**（同上） |
| `legIndex`（5） | 脚部装備差分 | **v1では未使用**（同上） |

解決順（先に一致したものを採用）:

1. 端末固有アート（v2 以降。`deviceName` 一致）
2. 属性 × 衣装ティアのベースアート
3. `null`（→ `PixelCharacter` フォールバック）

### 6-3. パレット・アクセサリー・オーラの実現方法

**パレット（12色）**: ベース立ち絵と同寸のアルファマスク `*_mask.webp` を 1 枚ずつ用意し、
髪の内側・衣装のトリム・機材のラインだけを白で塗る。ランタイムでこのマスクに
パレット色を乗せて合成する（Flutter の `BlendMode` 合成、または `ColorFiltered` + マスク）。
アセット追加はベースあたり 1 枚のみで 12 色展開できる。

**アクセサリー（7種）**: `manifest.json` に各ベースの「頭部アンカー座標」と「頭部幅」を持たせ、
アクセサリー画像はアンカー基準でスケール配置する。これによりアクセサリー画像は
ベース数に関係なく **7枚で済む**。

**オーラ（5種）**: アセット化しない。現行の `_drawAura` と同じ手続き描画を新ウィジェット側へ
移植し、属性色で描く。静かな背景を壊さないよう不透明度は現行より下げる。

### 6-4. トレードオフ: バリエーション総数の低下

| | 現行 | v1（本案） | v2目標 |
|---|---|---|---|
| 見た目の組み合わせ | 691,200 | 18 × 12（パレット） × 8（アクセ0含む） × 6（オーラ0含む） = **10,368** | 表情8軸を追加して 82,944 |

**これは意図的な後退である。** 691,200 通りの「ほぼ違いが分からないドット絵」より、
10,368 通りの「見て嬉しいイラスト」を選ぶ、という判断を明示的に置いている。
承認できない場合は §11 の未決事項として差し戻すこと。

緩和策として、`CharacterGenerator` のアクセサリー／オーラの出現確率
（現行: アクセ 50%・オーラ 75% で「なし」）を引き下げる案があるが、
これはドメイン層の変更になるため本RFCのスコープ外とし、別タスクとする。

### 6-5. URL対戦の互換性

`CharacterCodec` を変更しないため、**バージョン v3 のまま新旧クライアントが相互に対戦できる**。

- 旧クライアント → 新クライアント: 7バイトのビジュアル値から新アートが解決される
- 新クライアント → 旧クライアント: 同じバイト列がドット絵として描かれる
- 両者でステータス・属性・レアリティ・勝敗はすべて一致する（アートは presentation 層のみの差）

**同一URLを新旧クライアントで開くと見た目が異なる**点は仕様として受け入れる。
これを避けたい場合のみ codec v4 で `artId` を持つ必要があるが、
互換性コストに見合わないため**推奨しない**。

## 7. 12×12 ドット絵はどうなるか

**廃止しない。フォールバックと極小スロット用の描画系として残す。**

| 用途 | v1以降の扱い |
|---|---|
| アセット未整備のキャラ | `PixelCharacter` にフォールバック（＝アセット0枚でも全画面が現状のまま動く） |
| 図鑑一覧（24px）・Powerカード（28px） | `PixelCharacter` を継続使用。立ち絵は判読不能なため |
| インベントリ一覧（52px） | 立ち絵のバストアップクロップ or ドット絵。実機確認で決定（§11） |
| バトル・キャラ詳細・ガチャ演出・URLプレビュー | 新アートへ置き換え |
| アバタースタジオ | v1 は現状維持（カスタマイズ軸が v1 マッピングと噛み合わないため。§11） |

`pixel_character.dart` は**削除も改名もしない**。
新規に `CharacterArt` ウィジェットを追加し、その内部で
「resolver がキーを返せば画像 / 返さなければ `PixelCharacter`」を分岐させる。
呼び出し側は `PixelCharacter` → `CharacterArt` への差し替えのみで済む。

## 8. アセットパイプライン

### 8-1. 制作フロー

```
1. キャラクターシート作成（正面全身・設定年齢・職能・属性）
      ↓  §4-3 チェックリストで承認ゲート
2. 本制作（線画 → 塗り → リムライト）
      ↓
3. マスク書き出し（アクセント面のみのアルファマスク）
      ↓
4. 書き出し・最適化（WebP 変換 + 容量チェック）
      ↓
5. manifest.json 追記（アンカー座標・メタデータ・出典）
      ↓  §4-3 チェックリストで納品検収
6. リポジトリ追加 + pubspec 登録
```

### 8-2. 制作手段と権利上の確認事項

いずれを選ぶかは未決（§11）。それぞれ以下を満たすこと。

| 手段 | 確認事項 |
|---|---|
| 外部発注 | 商用利用・改変・再配布の可否を契約で明示。二次利用範囲（ストア画像・OGP・SNS）を含める |
| 生成AIによる制作 | 利用サービスの出力に関する権利条項の確認。学習データ由来の類似性リスクの確認。生成物を最終アセットとする場合は人手による修正・検収を必須とする |
| 自作 | 制作時間の見積もりを計画ファイルに記録 |

**本RFCおよび本PRでは最終PNG／画像アセットを生成しない。**
実装スライスで使うのは、寸法とアンカーの検証用プレースホルダのみとする。

### 8-3. フォーマット・解像度・容量バジェット

| 項目 | 値 | 根拠 |
|---|---|---|
| 原寸 | 1024 × 1536（2:3 縦） | 将来の大画面表示・演出まで耐える |
| 配信解像度 | 512 × 768（1枚） | 最大表示（キャラ詳細）でも 2x 相当を確保できる |
| 形式 | WebP（lossy, q=82） | Flutter Web / モバイル双方で対応。PNG 比で 1/5 前後 |
| 容量上限 | ベース1枚 **≤ 120KB** / マスク **≤ 30KB** / アクセサリ **≤ 20KB** | 下記の総量から逆算 |
| v1 総量目標 | **≤ 3.0MB** | 18×120KB + 18×30KB + 7×20KB ≒ 2.8MB |

**既存アセットに関する注意**: `assets/images/battle_bg.png`（1.3MB）、`title_bg.png`（1.2MB）、
`ogp.png`（1.0MB）はいずれも未最適化の PNG である。
キャラクターアート 3MB を追加する前に、これら背景の WebP 化を
**先行タスクとして実施すべき**（初回ロードのバジェット確保）。本RFCのスコープ外だが強く推奨する。

### 8-4. ディレクトリ構成

```
assets/characters/
  manifest.json                 # アート定義とメタデータ（唯一の真実）
  base/
    fire_standard.webp
    fire_standard_mask.webp
    fire_enhanced.webp
    fire_enhanced_mask.webp
    ...                         # 6属性 × 3ティア = 18組
  accessory/
    accessory_1.webp            # アンテナ
    ...                         # accessory_7.webp まで
  device/                       # v2以降: 端末固有アート
```

既存の `assets/characters/{heads,bodies,arms,legs}/`（`.gitkeep` のみ）は、
パーツ合成前提の旧構想の名残である。**v1 では使用しない**。
削除するかどうかは実装スライスの外で判断する（今回は触らない）。

### 8-5. manifest.json のスキーマ

```jsonc
{
  "schemaVersion": 1,
  "bases": [
    {
      "id": "fire_standard",
      "element": "fire",
      "tier": "standard",
      "image": "assets/characters/base/fire_standard.webp",
      "accentMask": "assets/characters/base/fire_standard_mask.webp",
      "size": [512, 768],
      "headAnchor": [256, 96],     // アクセサリ配置基準点（px, 画像座標）
      "headWidth": 132,            // アクセサリのスケール基準（px）
      "battleCrop": [0.0, 0.0, 1.0, 0.42], // バトル用バストアップ切り出し（左,上,右,下の割合）
      "meta": {
        "characterAge": 31,        // §4-3 必須: 20歳以上であること
        "role": "熱管理オペレーター",
        "author": "TBD",
        "license": "TBD",
        "reviewedAt": "TBD"        // §4-3 チェックリスト通過日
      }
    }
  ],
  "accessories": [
    { "index": 1, "image": "assets/characters/accessory/accessory_1.webp", "anchorScale": 1.0 }
  ]
}
```

- `manifest.json` はビルド時にアセットとして読み込み、起動時に一度だけパースしてメモリに保持する
- `characterAge` は表示に使わないが、**検収の証跡として必須**とする
- パース失敗時は例外を投げず、空マニフェストとして扱う（＝全キャラがドット絵にフォールバック）

### 8-6. ランタイムの読み込み

- 画像は `AssetImage` + `precacheImage` で扱う
- バトル開始前に**自機・敵機の2枚を先読み**し、バトル中のちらつきを防ぐ
- ガチャ演出は排出確定後に対象1枚を先読みしてから演出を開始する
- 一覧系（インベントリ・図鑑）では先読みしない。Flutter の標準キャッシュに任せる
- 読み込み失敗（デコード失敗・アセット欠落）時は `errorBuilder` で `PixelCharacter` にフォールバックする

## 10. リスク

| リスク | 影響 | 緩和策 |
|---|---|---|
| 100px 表示で立ち絵が潰れる | バトル画面の価値が出ない | 第1スライスで `battleCrop` を検証。ダメならレイアウト変更（表示サイズ引き上げ）を別タスク化 |
| 初回ロードが重くなる | Web 版の体験劣化 | WebP + 容量バジェット。背景 PNG の WebP 化を先行実施 |
| 見た目バリエーションの激減 | 「自分の端末のキャラ」感が薄まる | パレット12色 + アクセサリ + オーラで 10,368 通りを確保。v2 で表情差分を追加 |
| アート品質のばらつき | 一部キャラだけ浮く | §4-3 チェックリストによるシート段階での承認ゲート |
| 年齢表現が曖昧なアセットが混入 | 受け入れ不可 | §4-3 を必須基準として運用し、`manifest.meta.characterAge` を検収の証跡にする |
| 権利関係の未確認 | 公開後に差し替えが必要になる | 制作着手前に §8-2 の確認事項をクリアする |
